## 1. 문제 정의 — 무엇을 보정하는가

### 1.1 두 종류의 Extrinsic을 구분한다

| Extrinsic | 사용처 | 민감도 | 본 문서의 대상 |
|---|---|---|---|
| IMU ↔ LiDAR (센서 유닛 내부) | FAST-LIO2 내부 deskew/모션보상 | 매우 높음 (부정확하면 점군 자체가 왜곡) | **아니오** — OS1 유닛 자체 팩토리 캘리브레이션 영역, 별도 관리 |
| Vehicle(base_link) ↔ LiDAR(body) | `gnss_corrector_node`의 `body_to_base_link_x/y/z` | 상대적으로 낮음 (GNSS가 지속 보정) | **예** — 본 문서의 대상 |

### 1.2 Yaw는 이미 자동 보정되지만, 병진(XYZ)은 그렇지 않다

`gnss_corrector_node.cpp:947`의 `yaw_map = raw_yaw + dyaw`는 **회전 오차가 레버암을 통해 위치 오차로
증폭되는 것**을 막아준다(시스템설계서 §5 참조) — 이는 `dyaw`가 GNSS heading으로 지속 보정되기 때문에
자동으로 성립한다.

그러나 `body_to_base_link_x/y/z` 자체는 EKF 바깥에서, EKF 계산이 끝난 뒤 **그냥 더해지는 상수**다
(`cpp:950-952`). 이 값이 CAD와 실제 사이에 몇 cm 오차가 있어도, 이를 감지하거나 보정하는 어떤 피드백
루프도 코드에 없다.

- **단일-LIO 시스템**: 이 오차는 최종 위치에 걸리는 고정된 절대 오프셋일 뿐이라 상대적으로 무해하다
  (정지 분산 테스트로도 애초에 검출되지 않는다 — 표준편차는 노이즈를 보는 것이지 상수 바이어스를 보는
  것이 아니다).
- **Dual-LiDAR 시스템**: 전방·후방 각각의 CAD 오차가 서로 다르면, 두 스트림 사이에 **절대 없어지지 않는
  상수 바이어스 차이**가 생긴다. Final Fusion 단계는 이것이 노이즈인지 바이어스인지 구분하지 못하고,
  최종 위치에 몇 cm가 그대로 남을 수 있다.

### 1.3 현재 코드가 지원하는 파라미터 범위

`body_to_base_link_x/y/z` — **XYZ 3축 병진만 존재**한다. Roll/Pitch 오프셋 파라미터는 코드에 없다
(지상 AGV 특성상 2차 영향으로 간주해 생략된 것으로 추정). 따라서 본 절차의 1차 목표는 **XYZ 3-DOF
병진 보정**이며, Roll/Pitch까지 다루려면 코드에 파라미터를 추가하는 후속 작업이 필요하다(§7).

## 2. 왜 이 방법인가 — Pose-stream 기반 vs 점군 기반(ICP/NDT)

| 항목 | 점군 기반 (예: 워크스페이스의 `multi_lidar_calibration_ros2`, ICP/NDT) | Pose-stream 기반 (본 절차) |
|---|---|---|
| 전제조건 | 두 LiDAR가 **같은 장면을 동시에** 봐야 함(시야 중첩) | 전제조건 없음 — 각 스트림이 **이미 같은 절대좌표계(RTK)** 에 있음 |
| 이 차량에 적합한가 | 전방좌측/후방우측 대각선 배치는 시야가 거의 안 겹치므로 **부적합** | 시야 중첩과 무관하게 동작 — **적합** |
| 필요 데이터 | 특수 캘리브레이션 타겟/환경 | 일반 주행 데이터(직선+회전+S자)만 있으면 됨 |
| 구현 난이도 | 점군 정합 알고리즘·파라미터 튜닝 필요 | 병진 전용이면 선형 최소제곱으로 충분 (§4) |

**결론**: 15m 차량의 대각선 코너 배치라는 조건에서는 점군 기반 방법보다 Pose-stream 기반 방법이 명백히
더 적합하다.

### 2.1 그럼에도 ICP/NDT(점군 정합 기반) 캘리브레이션이 필요해지는 경우

Pose-stream 방법이 이 시스템에는 적합하지만, 다음 목적/상황에서는 ICP/NDT 기반 정합이 필요하거나 더
우월하다. 향후 요구사항 변경 시 재검토 기준으로 삼는다.

| 상황 | 이유 | 현재 시스템 해당 여부 |
|---|---|---|
| **점군 자체를 하나의 지도로 병합**해야 할 때 (정밀 3D 장애물 지도, 점군 시각화·중첩) | Pose-stream 방법은 "평균적으로 차량 위치가 일치하는가"만 검증한다. 두 pose가 잘 맞아도 점 단위로는 수 cm~각도 오차가 남을 수 있고, 점군을 실제로 합치면 이 오차가 흐릿한 겹침(ghosting)이나 원거리에서 큰 어긋남으로 바로 드러난다. 점 단위 정합에는 점 단위 캘리브레이션이 필요하다. | 해당 없음 (FR-2/FR-3에서 점군 병합을 명시적으로 배제) — **단, 향후 장애물 지도 구축 등이 요구사항에 추가되면 재검토 필요** |
| **Roll/Pitch까지 정밀한 6-DOF**가 필요할 때 | Pose-stream 방법은 2D 평면 가정(XY 병진 + yaw)만 다룬다 — GNSS는 애초에 수평 위치·헤딩만 주므로 roll/pitch를 원천적으로 관측할 수 없다. | 해당 없음 (현재 코드에 roll/pitch 파라미터 자체가 없음, §1.3) |
| **RTK GNSS 정확도(~2cm)보다 더 정밀한 캘리브레이션**이 필요할 때 | Pose-stream 방법의 정확도 한계는 기준으로 쓰는 GNSS 자체의 정확도다 — 기준보다 더 정밀하게 캘리브레이션할 수 없다. 점군의 풍부한 기하 정보를 직접 쓰는 ICP/NDT는 시야가 겹치는 조건에서 서브cm급도 가능하다. | 목표 정밀도(§6.1, <5cm)가 GNSS 정확도 범위 내이므로 해당 없음 |
| **두 LiDAR 시야가 실제로 겹칠 때** | 시야가 겹치면 ICP/NDT(`multi_lidar_calibration_ros2` 등)가 다시 타당한 선택지가 되며, 위 항목들과 결합되면 오히려 더 적합할 수 있다. | 해당 없음 (전방좌측/후방우측 대각선 배치는 시야가 거의 겹치지 않도록 의도적으로 설계됨) |
| **GNSS 자체를 신뢰할 수 없는 환경/용도**일 때 | Pose-stream 방법은 "두 스트림 모두 GNSS로 절대좌표에 붙어있다"는 전제에 전적으로 의존한다. 운용 대부분이 GNSS 음영구간(실내, 상시 협곡 통과 등)이라면 두 pose 불일치가 진짜 캘리브레이션 오차인지 단순 드리프트인지 구분이 안 된다. | 항만 개활지 위주 운용이며 RTK 확보를 전제로 하므로 해당 없음 — GNSS 음영이 지배적인 별도 용도에 이 아키텍처를 재사용할 경우 재검토 |
| **교차검증(defense-in-depth) 목적** | 두 라이다 시야가 부분적으로라도 겹치는 구간(예: 차량 측면)이 있다면, 그 구간에서 ICP로 독립 2차 검증이 가능하다. GNSS 자체가 방향에 상관된 편향(멀티패스 등)을 가지면 두 pose가 "일치하지만 같은 방향으로 함께 틀려 있는" 상황을 pose 비교만으로는 못 잡지만, 국소 기하 정합은 잡을 수 있다. | 선택적 — 시야가 부분적으로 겹치는 구간이 확인되면 §7 후속 검토 항목으로 추가 고려 |

**요약**: 이 시스템(15m 차량, 비중첩 대각선 배치, RTK급 GNSS 확보)에서는 Pose-stream 방법이 맞는
선택이며, ICP/NDT는 "점군 자체를 합쳐야 하거나, 3D 회전 전체가 필요하거나, 시야가 겹치거나, GNSS를
못 믿을 상황"일 때 꺼내는 도구다.

## 3. 관측 가능성(Observability)과 기준(reference) 고정

두 스트림의 병진 오프셋 오차를 **동시에 각각** 절대값으로 복원하는 것은 불가능하다 — 두 스트림을 서로
비교해서 알 수 있는 것은 **상대적 차이**뿐이다 (두 오프셋을 똑같이 한쪽으로 밀어도 서로 간의 일치 정도는
변하지 않기 때문, gauge freedom).

**따라서 한쪽을 기준으로 고정한다.** 본 절차는 **전방(front) 스트림의 CAD 값을 기준(변경하지 않음)**으로
삼고, **후방(rear) 스트림의 보정치만** 구한다. (반대로 해도 무방하나, 문서 전체에서 일관되게 전방을
기준으로 한다.)

> 절대 진위(true base_link 위치)까지 알고 싶다면 별도의 외부 기준(예: 정밀 측량된 기준점)이 있어야
> 하며, 이는 본 절차의 범위를 벗어난다. 본 절차는 "두 스트림이 서로 일치하게" 만드는 것이 목표다.

## 4. 수학적 정식화

### 4.1 데이터 소스 — `/odometry/map`을 사용하는 이유

각 인스턴스가 발행하는 `/odometry/map`(디버깅용, `publishMapOdom`, `cpp:842-877`)은 `body_to_base_link`
오프셋이 **적용되기 전**의 "GNSS로 보정된 body(IMU) 위치"다. 이미 오차가 있을 수 있는 현재
`body_to_base_link` 값이 섞이지 않은 순수한 값이므로, 보정치를 구하는 입력으로 이 토픽을 사용한다
(`/lpc/localization/pose_update`가 아님에 주의).

- `B_front(t)`, `B_rear(t)`: 각 인스턴스의 `/odometry/map` 위치 (map 프레임, body 기준)
- `yaw_front(t)`, `yaw_rear(t)`: 각 인스턴스의 `/odometry/map` orientation에서 추출한 yaw (이미 GNSS로
  보정된 값)

### 4.2 잔차(residual) 정의

전방·후방 각각 현재 CAD 값(`t_front_CAD`, `t_rear_CAD`, 3-vector)을 적용했을 때의 base_link 위치는:

```
base_link_front(t) = B_front(t) + R(yaw_front(t)) · t_front_CAD
base_link_rear(t)  = B_rear(t)  + R(yaw_rear(t))  · (t_rear_CAD + Δt_rear)
```

여기서 `R(yaw)`는 z축 회전만 적용하는 2D 평면회전(x,y에 대해)이며, z축 오프셋은 회전 없이 그대로 더해진다
(현재 코드 방식과 동일, `cpp:942-952`). 두 base_link 위치가 같아야 하므로 잔차는:

```
r(t) = base_link_front(t) − base_link_rear(t)
     = [B_front(t) + R(yaw_front(t))·t_front_CAD] − [B_rear(t) + R(yaw_rear(t))·t_rear_CAD]
       − R(yaw_rear(t)) · Δt_rear
```

### 4.3 선형 최소제곱으로 충분하다 (Ceres 불필요, XYZ-only 범위에서는)

`yaw_rear(t)`는 이미 알려진 값(각 시점에서 관측된 값)이므로, `R(yaw_rear(t))·Δt_rear`는 `Δt_rear`에 대해
**선형(linear)**이다. 즉 x,y 성분은 다음 정규방정식으로 바로 풀 수 있다:

```
b(t) = [B_front(t) + R(yaw_front(t))·t_front_CAD] − [B_rear(t) + R(yaw_rear(t))·t_rear_CAD]   (2-vector, x,y만)
A(t) = R(yaw_rear(t))                                                                          (2x2)

Δt_rear_xy = argmin Σ_t w(t) · ‖A(t)·Δt_rear_xy − b(t)‖²
           = ( Σ w(t) A(t)ᵀA(t) )⁻¹ ( Σ w(t) A(t)ᵀ b(t) )     ← 가중 정규방정식, 닫힌 형태 해

Δz_rear = ( Σ w(t) b_z(t) ) / ( Σ w(t) )       ← z는 회전이 없으므로 가중 평균으로 충분
```
가중치 `w(t)`는 해당 시점 두 스트림의 quality(0~5)를 곱한 값 등으로 설정하여, 어느 한쪽이라도 quality가
낮은 구간(freeze, FLOAT/SINGLE 등)의 영향을 자동으로 줄인다.

> **비선형 솔버(Ceres 등)가 필요한 경우**: 향후 Roll/Pitch까지 확장하면(§7) 3차원 회전 합성이 비선형이
> 되므로 그때는 Ceres 등으로 전환한다. 현재 범위(XYZ-only)에서는 위 닫힌 형태 해로 충분하며 구현이 훨씬
> 간단하다.

## 5. 데이터 수집 절차

### 5.1 사전 조건

- 양쪽 인스턴스 모두 RTK FIX, quality=5 안정 상태에서 시작.
- `set_origin`/`set_datum`이 양쪽 인스턴스에 이미 정상 적용되어 있을 것 (시스템설계서 §D-5 이슈와 연계 —
  두 인스턴스의 map 원점이 일치해야 이 절차 자체가 의미를 가짐).

### 5.2 주행 시나리오

| 구간 | 목적 | 권장 거리/시간 |
|---|---|---|
| 직선 주행 | X축(전후) 오프셋 관측 | 30m 이상, 왕복 권장 |
| 제자리/저속 회전 | yaw 의존성을 통해 X/Y 커플링 관측, 회전 중 일관성 확인 | 360° 최소 1회 |
| S자/곡선 주행 | 다양한 heading 조합 확보 → 관측 가능성(observability) 확보 | 수 회 반복 |
| 전체 시간 | 통계적으로 충분한 샘플 확보 | 10~20분 권장 (동료 의견 반영) |

전 구간에서 quality < 4인 구간은 사후 필터링으로 제외한다 (가중치 0 처리, §4.3).

### 5.3 데이터 로깅

```bash
ros2 bag record /gnss_corrector_front/odometry/map /gnss_corrector_rear/odometry/map \
                /gnss_corrector_front/pose_update /gnss_corrector_rear/pose_update
```
(토픽명은 기술명세서 §3.1의 네임스페이스 규칙을 따름. `pose_update`는 quality 값 추출용으로 함께 기록)

## 6. 계산 절차 (알고리즘 요약)

1. rosbag에서 `B_front(t)`, `B_rear(t)`, `yaw_front(t)`, `yaw_rear(t)`, `quality_front(t)`, `quality_rear(t)`
   를 추출.
2. 두 스트림의 타임스탬프를 동기화 (가장 가까운 시각끼리 매칭, 허용 오차 예: 20ms 이내만 채택 — 각
   인스턴스는 독립된 FAST-LIO2 주기로 발행되므로 완전히 동시에 발행되지 않음).
3. `quality_front(t) < 4 OR quality_rear(t) < 4`인 시점 페어는 제외.
4. §4.3의 가중 정규방정식으로 `Δt_rear = (Δx, Δy, Δz)` 계산.
5. 잔차 `r(t)`의 사후 표준편차를 계산하여 보정 품질을 확인 (§6.1).
6. `body_to_base_link_x/y/z`(rear 인스턴스) 파라미터에 `t_rear_CAD + Δt_rear`를 반영.
7. 보정된 파라미터로 재기동 후, 동일한 주행(또는 축소판)을 재수행하여 잔차가 충분히 줄었는지 확인.

### 6.1 보정 품질 판정 기준

| 지표 | 기준 |
|---|---|
| 보정 전 잔차 표준편차 | 참고용 (보정 필요성 정량화) |
| 보정 후 잔차 표준편차 | < 5cm (목표, 시스템설계서 §5.4 수치 근거와 정합) |
| `Δt_rear` 크기 | CAD 대비 과도하게 크면(예: >20cm) 최적화 오류 또는 CAD 자체의 큰 오기입 가능성 — 재검토 |

## 7. 한계 및 후속 검토 사항

1. **Roll/Pitch 미지원**: 현재 코드에 해당 파라미터가 없다. 필요성이 확인되면(예: 마운트 브라켓의
   기계적 틀어짐이 유의미하다고 판단될 경우) `body_to_base_link_roll/pitch` 파라미터를 `gnss_corrector_node`
   에 추가한다. **이 경우 §4의 Pose-stream 선형 정식화를 확장하기보다, §9의 정지 평면타겟 기반 방법으로
   완전 6-DOF를 직접 구하는 것을 권장한다** — 별도 비선형 솔버 구현 없이도 기존 `multi_lidar_calibration_ros2`
   (ICP/NDT)로 바로 처리 가능하다.
2. **Yaw 오프셋의 명시적 진단**: 런타임에는 `dyaw`가 마운트 yaw 오차를 자동 흡수하므로 별도 보정
   파라미터가 필요 없지만, 본 절차 수행 시 **참고용으로 전/후방의 상대 yaw 바이어스를 함께 리포트**할
   것을 권장한다 — 만약 이 값이 비정상적으로 크면(예: 5° 이상) 소프트웨어가 자동 흡수한다 해도 물리적
   재설치를 검토할 신호로 삼는다 (큰 각도 오차는 GNSS 업데이트 주기 사이에서 상대적으로 더 큰 과도 오차를
   유발할 수 있음, 시스템설계서 §5.4의 수치 예시는 작은 각도 가정임에 유의).
3. **재검증 주기**: 항만은 진동·충격이 잦은 환경이므로(failure case 문서 F-2, B-4 참조), 정기 점검
   주기(예: 6개월 또는 물리적 충격 이벤트 발생 시)마다 축소판 절차(§5.2의 직선+회전만, 5분 내외)를
   재수행하여 `Δt_rear`가 크게 변하지 않았는지 확인할 것을 권장한다.
4. **두 인스턴스 모두 CAD가 틀렸을 가능성**: 본 절차는 전방을 기준으로 고정하므로, 만약 전방 CAD 값도
   실제로 틀려 있다면 그 오차는 보정되지 않고 그대로 최종 출력에 남는다. 절대 정확도가 중요한
   운용(예: ASC 크레인 핸드오버, 시스템설계서 §6 항만 적용성 평가의 "△/⚠️" 등급 작업)에서는 정밀 측량
   기준점을 이용한 절대 검증을 별도로 검토한다.

## 9. 대안/보완 방법 — 정지 상태 평면 타겟 기반 6-DOF 캘리브레이션

### 9.1 개요 — 언제 이 방법을 쓰는가

§2.1에서 정리했듯 Roll/Pitch를 포함한 완전 6-DOF가 필요하거나, GNSS 정확도(~2cm)보다 더 정밀한 결과가
필요하면 점군 정합(ICP/NDT) 기반 방법이 적합하다. 다만 **주행 중** 두 라이다의 시야를 정합하려는 시도는
① 대각선 배치 특성상 순간 중첩이 거의 없고 ② 설사 시간차 중첩을 이용하더라도 항만은 컨테이너가 계속
이동하는 동적 환경이라 대응점 매칭이 오염되기 쉽다는 문제가 있다 (검토 기록: 이동 중 정합 방식은 기각).

**해결책**: 차량을 **정지**시키고, 두 라이다가 동시에 볼 수 있는 위치에 평면 구조물(타겟)을 배치하여
완전히 통제된 환경에서 6-DOF를 구한다. 정지 상태이므로 항만의 동적 요소(크레인 작업 등) 문제가
원천적으로 사라진다.

### 9.2 FAST-LIO2 / IMU 융합이 필요 없는 이유

**결론: 필요 없다. `/ouster1/points`, `/ouster2/points` 원시 점군만으로 충분하다.**

FAST-LIO2의 IMU 융합(deskew)이 존재하는 이유는 **센서가 스캔하는 동안 차량이 이동하면서 점군이
왜곡되는 것**을 보정하기 위해서다. 본 절차는 차량이 완전히 정지한 상태에서 수행하므로:

- 스캔 도중 차량(=센서 자체)의 거시적 이동이 없으므로 왜곡시킬 요인 자체가 없다.
- 센서 내부의 회전(초당 스캔 완료를 위한 미러 회전 등)은 Ouster 드라이버가 자체적으로 이미 타임스탬프
  기반으로 정확히 반영하여 점군을 생성한다 — 이건 FAST-LIO2와 무관하게 센서 자체가 항상 하는 일이다.
- 따라서 정지 상태의 원시 점군은 그 자체로 이미 "깨끗한" 기하 데이터이며, FAST-LIO2/GNSS-EKF 스택
  전체를 기동할 필요가 없다.

이는 실무적으로도 큰 이점이다 — 이 절차는 **RTK FIX나 GNSS 신호와 무관**하며(§5.1의 Pose-stream 방법이
RTK FIX·quality≥4를 전제조건으로 요구했던 것과 대조적), FAST-LIO2/gnss_corrector_node 튜닝이 끝나기
**이전 단계**에서도, 심지어 실내 차고에서 GNSS 없이도 수행할 수 있다. 커미셔닝 순서상 이 방법을 먼저
수행하고, 이후 Pose-stream 방법(§1~§8)이나 실제 주행 검증으로 넘어가는 것을 권장한다.

> 참고: PTP 시간동기화 자체는 여전히 유효하고 유용하다 — 두 라이다의 점군을 "같은 정지 순간"으로
> 정확히 맞춰 누적/평균하는 데 쓰이며, 각 센서 자신의 내부 deskew(있다면)에도 쓰인다. 다만 이건
> "IMU와 LiDAR를 융합하는" FAST-LIO2 레벨의 처리와는 다른, 훨씬 가벼운 요구사항이다.

### 9.3 사전 조건 확인 — 중첩 시야가 실제로 존재하는가

OS1-32는 360° 회전형 라이다이므로, 차체/적재함에 가려지는 방향 외에는 원칙적으로 시야가 열려 있다.
전방좌측·후방우측처럼 대각선 배치라도, **차체에서 충분히 이격된 지점**(수 m~십여 m)에서는 양쪽 다 볼 수
있는 영역이 존재할 가능성이 높다 — 다만 이는 실제 차체/적재함 형상에 따라 달라지므로 **반드시 실차에서
먼저 확인**한다.

**확인 절차**: 두 라이다의 원시 점군(`/ouster1/points`, `/ouster2/points`)을 RViz에 동시에 띄우고
(각각 알고 있는 CAD 기준 TF로 임시 정렬), 차량 주변을 둘러보며 두 점군이 같은 물리적 구조물을 동시에
포착하는 영역이 있는지 육안으로 확인한다.

### 9.4 타겟 배치 요구사항

완전 6-DOF(3-DOF 회전 + 3-DOF 병진)를 관측하려면 평면 하나로는 부족하다 — 평면 법선(normal) 방향이
정보를 주는 축만 구속하기 때문에, **서로 평행하지 않은 평면 3개 이상**이 필요하다 (고전적인 평면 기반
외부 캘리브레이션의 기본 요구조건).

| 항목 | 권장 사항 |
|---|---|
| 평면 개수 | 최소 3개, 서로 다른 법선 방향 (예: 정면 벽 1개 + 측면 벽 1개 + 지면) |
| 특수 타겟 필요 여부 | 불필요 — 평평하기만 하면 됨. 지면(수평면) + 기존 항만 구조물(안벽, 컨테이너 벽면, 벽체)을 활용 가능하며, 마땅한 게 없으면 평판(합판 등)을 세워 배치 |
| 이격 거리 | 두 라이다 중 어느 쪽 시야도 차체에 가리지 않는 거리 (§9.3에서 확인한 중첩 영역 내) |
| 배치 다양성 | 평면들이 서로 다른 위치·각도에 분산되어 있을수록 관측 가능성이 좋아짐 |

### 9.5 데이터 수집 절차

1. 차량을 완전히 정지 (엔진 진동 등 최소화 — 가능하면 시동 off 상태 권장).
2. `/ouster1/points`, `/ouster2/points`를 수 초~수십 초간 기록 (`ros2 bag record`).
3. 여러 프레임을 누적/평균하여 노이즈를 줄인다 (정지 상태이므로 단순 포인트 누적만으로 가능, 좌표 보정
   불필요).

### 9.6 계산 절차 — 기존 도구 재사용

이 시야 중첩 조건에서는 워크스페이스에 이미 있는 `multi_lidar_calibration_ros2`(ICP 또는 NDT) 노드를
그대로 사용할 수 있다:

```bash
# NDT 방식 권장 (README상 권장 방식)
ros2 launch multi_lidar_calibration_ros2 multi_lidar_calibration_ndt.launch.xml \
  input/source_pointcloud:=/ouster2/points \
  input/target_pointcloud:=/ouster1/points \
  initial_pose:=[<CAD 기준 대략적 상대 위치/자세 6개 값>]
```
- `initial_pose`에는 CAD 값 기준으로 계산한 두 body 프레임 간 대략적인 상대 변환을 초기값으로 넣는다
  (완전히 0으로 두지 않는 것이 ICP/NDT 수렴에 유리).
- 결과로 나오는 6-DOF 변환이 **후방(rear) 프레임 → 전방(front) 프레임**(또는 그 역, 도구 설정에 따라
  방향 확인 필요)의 보정된 상대 변환이다.

### 9.7 기준 고정 — Pose-stream 방법과 동일 원칙

이 방법도 **상대 변환**만 알려준다 — 절대적으로 어느 쪽이 "옳은지"는 알 수 없다(§3의 gauge freedom과
동일한 제약). 따라서 동일하게 **전방 CAD 값을 기준으로 고정**하고, 이번에 구한 상대 변환으로부터 후방의
`body_to_base_link_x/y/z`(및 필요시 신규 `roll/pitch` 파라미터)를 역산하여 반영한다.

### 9.8 두 방법 비교 및 상호 보완 관계

| 항목 | Pose-stream (§1~§8) | 정지 평면타겟 (§9) |
|---|---|---|
| 획득 가능한 DOF | XYZ 3개만 | 완전 6개 (XYZ+Roll/Pitch/Yaw) |
| 정확도 한계 | GNSS 정확도(~2cm)에 종속 | 점군 정합 정밀도 (통상 더 정밀, mm~cm급) |
| 전제조건 | RTK FIX, quality≥4, 두 인스턴스 set_origin 완료 | 중첩 시야 존재 확인(§9.3), 평면 타겟 배치 |
| 필요 스택 | FAST-LIO2 + gnss_corrector_node 전체 기동 | 원시 LiDAR 드라이버만 (`ouster_ros`) — GNSS/EKF 불필요 |
| 소요 시간 | 10~20분 주행 | 정지 상태 수 분 (준비 시간 제외) |
| 실행 가능 시점 | 커미셔닝 후반(EKF 튜닝 완료 후) | 커미셔닝 **초반**(가장 먼저 수행 가능) |
| 동적 환경 영향 | 없음 (GNSS 절대좌표 기준이라 주변 환경 무관) | 없음 (정지 상태라 무관) — 단, 이동 중 정합(기각된 방식)이었다면 영향 컸을 것 |

**권장 순서**: ①(먼저) §9 정지 평면타겟 방법으로 6-DOF 초기 보정 → ②(그다음) FAST-LIO2/GNSS-EKF 스택
기동 후 §1~§8 Pose-stream 방법으로 XYZ 잔차를 실주행 조건에서 재검증 → 두 방법의 결과가 서로 크게
어긋나면(예: 수 cm 이상) 원인 재조사.

- [ ] 서로 평행하지 않은 평면 3개 이상을 중첩 영역 내에 확보 (기존 구조물 또는 평판 배치)
